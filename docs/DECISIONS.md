# Decisions

ADR-style log. Add new entries at the bottom; do not rewrite accepted ones, supersede them.

## ADR-001: Configuration is validated in one place

- Status: accepted
- Context: env vars were read directly from `process.env` in several places and booleans were coerced incorrectly.
- Decision: `packages/config` (`loadEnv`) is the only reader of configuration; apps use the parsed object. Booleans accept only `true`/`false`; taxonomy creation defaults to off.
- Consequence: every new variable must be added to the schema and `.env.example`.

## ADR-002: WordPress endpoint is the REST base URL

- Status: accepted
- Decision: `OPENBLOG_WORDPRESS_ENDPOINT` is `https://site/wp-json/wp/v2` without `/posts`; the publisher appends resource paths.

## ADR-003: Ghost is documented as not implemented

- Status: superseded by ADR-029
- Context: `GhostPublisher` built a payload and returned success without any HTTP call.
- Decision: Ghost is removed from the factory, env schema, `.env.example` and README until it is implemented (Post-MVP). The class stays only as a placeholder whose `publish` fails with `not_implemented`, so no publisher can claim success without doing the work.

## ADR-004: Tests assert real behavior against current contracts

- Status: accepted
- Decision: the suite must be green in CI, must not depend on `console` output, and WordPress tests use injected taxonomy fakes. Coverage is reported in CI without a threshold.

## ADR-005: `graphify-out/` is not tracked in git

- Status: accepted
- Context: `graphify-out/` is 1.5 MB of generated graph data (cache, `graph.json`, `graph.html`, report) committed without explanation. It goes stale on every change.
- Decision: untrack it and add it to `.gitignore`. Anyone who wants it regenerates it locally with `graphify`.

## ADR-006: `.github/copilot-instructions.md` is kept, but Graphify is optional

- Status: accepted
- Context: the file made Graphify mandatory for architecture questions, which no longer works when `graphify-out/` is absent.
- Decision: keep the file for Copilot users and reword the Graphify section as optional ("when `graphify-out/graph.json` exists locally"). `CLAUDE.md` remains the primary instruction file.

## ADR-007: Markdown assembler is not part of the workflow

- Status: accepted
- Decision: the workflow publishes through `DefaultPublisherManager`; `createMarkdownAssembler` is unused scaffolding and is a candidate for removal in the scaffolding cleanup issue.

## ADR-008: LLM JSON replies go through one validated helper with retry

- Status: accepted
- Context: JSON extraction was copy-pasted in three agents plus the planner, malformed replies aborted the run, and normalization (slice, empty-string defaults) hid invalid output.
- Decision: `generateStructured` (`packages/agents/src/structured-output.ts`) extracts JSON, validates with Zod and re-prompts with the validation error (default 3 attempts, `maxAttempts` per agent), then throws `StructuredOutputError` with the truncated last reply. Schemas only do safe normalization (trim, slugify, tag de-dup/cap, category canonicalization) and reject empty slug/title/h1, over-long title/description and categories outside the allowed list.
- Consequence: no silent truncation; a model that keeps violating limits fails the run with a descriptive error. Provider failures (`ProviderError`) are not retried here, ADR for providers covers them.

## ADR-009: Remove unused scaffolding; wire dependencies explicitly

- Status: accepted (2026-10-21)
- Context: the repository carried empty marker interfaces, tool stubs, a tsyringe container nothing imported and duplicate `ILogger`/`IPublisher` contracts.
- Decision: removed `@openblog/core` (interfaces and DI container, plus `tsyringe`/`reflect-metadata`), `@openblog/tools` (stubs and the unused Markdown assembler, which supersedes the note in ADR-007), `@openblog/sdk` (re-export barrel with no consumers), `apps/dashboard` (one-line stub), the empty agent folders (`planner`, `writer`, `research`, `publisher`, `memory`, `analytics`) and the `IAgent` aliases in `seo`/`editor`, the placeholder `Node`/`Edge`/`Workflow` types in `@openblog/graph`, and the unused `OpenBlogError`/`isNonEmptyString`/`KeyValue` in `@openblog/shared`.
- Kept: `@openblog/shared` (only the constants the server uses) and `@openblog/types` (only `Identifier`, used by storage and publishers). A ts-prune pass also removed the unused `VersionInfo`/`Environment` types and the storage `ICacheStore`/`IMemoryStore` stubs. `ILogger` lives only in `@openblog/logger` and `IPublisher` only in `@openblog/publishers`.
- Decision: dependencies are wired with explicit constructors and factory functions; no DI container.
- Consequence: re-introduce a package (plugin SDK, dashboard, research tools) only together with working code that uses it.

## ADR-010: The workflow depends on ports; agents own prompts

- Status: accepted (2026-10-21)
- Context: the workflow file embedded the planner/writer prompts and parser, built `DefaultPublisherManager` itself and redefined the memory contract.
- Decision: `@openblog/graph` only orchestrates. It defines ports in `packages/graph/src/ports.ts` (`LlmPort`, `PublishPort`, `TaxonomyPort`, `MemoryPort`) and `createArticleGenerationWorkflow` receives them (`llm`, `publisher`, `taxonomy`, `memory`). The CLI is the bootstrap: it builds `DefaultPublisherManager`, the taxonomy adapter and the memory service. Planner and writer are agents like the others; all prompts live in `packages/agents/src/prompts/*` with a `*_PROMPT_VERSION` constant.
- Consequence: graph imports only types from adapter packages; the workflow is tested end-to-end with fakes. Bump the version constant when a prompt changes.

## ADR-011: One composition root builds the application from config

- Status: accepted (2026-10-21)
- Context: the CLI built providers, publishers, taxonomy and the workflow itself; WordPress taxonomy providers were created twice and default categories/tags were hard-coded.
- Decision: `createApplication(config, overrides?)` in `packages/app` is the only place adapters are constructed. It returns `{ workflow, info, dispose }`; `overrides` replace adapters in tests. WordPress taxonomy providers are built once and shared by the publisher and the classifier. Static categories/tags come from `OPENBLOG_TAXONOMY_CATEGORIES`/`_TAGS` or `OPENBLOG_TAXONOMY_FILE` (lists win over the file); with nothing configured the only category is `OPENBLOG_TAXONOMY_DEFAULT_CATEGORY`.
- Consequence: the CLI (`runCli`) only handles arguments and exit codes, and the server can build the same application (`buildServer({ application })`). The previous built-in category/tag lists are gone: set the variables to restore a taxonomy.

## ADR-012: A run is `published` only when the publisher confirms

- Status: accepted (2026-10-21)
- Context: the workflow never checked `publishResult.success`, so a failed publish was stored as `completed`, the CLI logged `Article saved` and exited 0.
- Decision: `ArticleWorkflowResult.status` is `published | needs_review | failed` and `failure` carries `{ step, code, message }`. A failed or missing publish result yields `failed` with the publisher's error code. Persisted statuses are `started -> running -> published | needs_review | failed` with `failed_step` and `error_code` columns. `finishWorkflow` stores the article even when publishing failed. A throwing step raises `WorkflowStepError` (step, code) and is stored via `failWorkflow`. The CLI exits non-zero unless the status is `published`.
- Consequence: `needs_review` is only defined, not produced (quality-gate issue). Old `completed` rows are not migrated.

## ADR-013: Workflow state is typed per step and validated where it is produced

- Status: accepted (2026-10-21)
- Context: every node re-parsed the whole state and cast it back, `seoOutput`/`publishResult` were `unknown`, an empty passthrough schema existed only to admit the initial `{}`, and empty strings stood for "not produced yet".
- Decision: the `Annotation` fields are typed (`SeoOutput | undefined`, `PublishResult | undefined`, ...) and a node's return type is checked against the state update. Each node validates its output with the Zod schema of its agent. `currentArticle(state)` returns the edited text once it exists. `run()` takes `{ topic }` and returns `ArticleWorkflowResult`, a union of `published` (with a confirmed `publishResult`) and `failed`.
- Consequence: `articleWorkflowStateSchema` and the empty-object workaround are gone. A missing field after a step is a wiring bug and throws.

## ADR-014: Storage is versioned, transactional and keeps step artifacts

- Status: accepted (2026-10-21)
- Context: the DB directory was never created, multi-statement operations were not atomic, the schema was a single `CREATE TABLE IF NOT EXISTS` block, outputs of intermediate steps were lost, and a failed first run counted as the original of a duplicate.
- Decision: the connection creates the DB directory; `data/` and `*.db*` are git-ignored. Migrations are an ordered list applied under `BEGIN IMMEDIATE` and tracked with `PRAGMA user_version` (v1 is the original schema and adopts unversioned databases; v2 adds `workflow_steps` and `articles.publish_remote_{id,url,status}`). Repositories are synchronous; `MemoryService` wraps `beginWorkflow` and `finishWorkflow` in one transaction. Each workflow step execution is stored in `workflow_steps` (output or error, attempt number) through `MemoryPort.recordStep`; a recording failure only logs a warning. Duplicates are detected against published runs only.
- Consequence: never edit a released migration, append one. `topics.first_workflow_id` is informational. Resuming runs from stored steps is a later issue.

## ADR-015: Resume uses our own `workflow_steps`, not a LangGraph checkpointer

- Status: accepted (2026-10-21)
- Context: a failed run discarded its generated content, so a retry paid for planner and writer again. LangGraph offers checkpointers (e.g. a SQLite saver) that snapshot graph state per super-step.
- Decision: keep `workflow_steps` (ADR-014) as the only checkpoint. Every node stores its output through `MemoryPort.recordStep` before the next one starts. `workflow.resume(workflowId)` loads the run with `MemoryPort.loadWorkflow`, validates the latest successful output of each step with the same Zod schemas the nodes use, seeds the graph state with them and marks those steps as completed so their nodes are skipped. The failed step is executed again with the next attempt number. A publish the publisher rejected is not a completed step, so it is retried. Resuming a `published` run, an unknown id, or without a memory store throws `WorkflowResumeError` and changes nothing.
- Consequence: SQLite stays the single store and the checkpoint format is our own JSON, reviewable in SQL; there is no dependency on a LangGraph checkpoint package. Resume is a workflow API only; the CLI flag is a separate issue. A step whose output schema changes between versions fails validation on resume instead of being silently reused.

## ADR-016: WordPress publisher sends sanitized HTML and supports Application Passwords only

- Context: the publisher posted raw Markdown, dropped the slug, ignored the response and accepted a regular password that the core REST API rejects.
- Decision: Markdown is converted with `marked` and sanitized with `sanitize-html` before it is sent. The endpoint must end in `/wp-json/wp/v2` (trailing slashes and `/posts` are stripped). Authentication is Basic with an Application Password; `OPENBLOG_WORDPRESS_PASSWORD` is removed. The post `id`, `link`, `status` and `slug` are parsed with Zod and returned in `PublishResult.metadata`; requests time out after 15s by default and failures carry a classified error code.

## ADR-017: WordPress taxonomy resolution policy

- Context: term creation hit an invalid URL, the cache "invalidation" returned an empty list, only the first 100 terms were read, and the category fallback/creation order was undocumented.
- Decision: an unknown category resolves to `OPENBLOG_TAXONOMY_DEFAULT_CATEGORY` and is never created (resolution fails if the default does not exist either). An unknown tag is created only when `OPENBLOG_TAXONOMY_ALLOW_CREATE=true`, otherwise it is skipped with a warning. Names are matched trimmed, case-insensitive and HTML-entity-decoded; tags are de-duplicated and capped at `OPENBLOG_TAXONOMY_MAX_TAGS`. Terms are read across all pages (`X-WP-TotalPages`), and a created term is added to the cache so later lookups in the same run neither re-create nor lose it. One provider pair per site is built in `createApplication`.

## ADR-018: Content validation is a pure rule module with configurable thresholds

- Context: nothing checked the length, structure or sanity of generated output before publication.
- Decision: `validateArticle(input, rules)` in `packages/agents/src/quality` returns `{ passed, violations[] }` with no I/O and no LLM calls. Each violation has a `code`, a `severity` (`error` fails the article, `warning` does not) and a message that is reused in regeneration prompts (`formatViolations`). Rules whose input is absent are skipped. Defaults (`DEFAULT_ARTICLE_RULES`): 1000-2200 words (the writer prompt asks 1200-1800; the range tolerates model drift), at least 3 H2 sections, no H1, 60% outline coverage by H2 headings (half of an item's significant words must appear), balanced code fences, no placeholder or AI-disclaimer phrases (`forbiddenPatterns`), edited/draft word ratio between 0.7 and 1.3, title <= 60, meta description <= 155, valid slug, no repeated paragraph of 8+ words. Code blocks are excluded from heading, placeholder and repetition checks.
- Consequence: thresholds are overridden by passing a partial rules object; wiring them to environment variables and to the workflow is a separate issue.

## ADR-019: Quality gate with bounded regeneration

- Context: the graph was a straight line, so any output was published.
- Decision: a `quality` node runs after `seo` and calls `validateArticle` (ADR-018) on the edited text, the writer draft, the outline and the SEO output. If it passes, the run goes on to classification and the publisher. If it fails and fewer than `OPENBLOG_QUALITY_MAX_ATTEMPTS` (default 2) regenerations were done, a `regenerate` node adds the violations to the writer prompt and the writer, editor, seo and quality nodes run again. Otherwise the article is still classified (so it is complete for a later review), stored with status `needs_review`, and the publisher is skipped. `max attempts` counts regenerations, so the worst case is 1 + N writer/editor/seo rounds. LLM calls and tokens are counted per run (AsyncLocalStorage around the tracked provider) and logged with every decision.
- Consequence: `ArticleWorkflowResult` gains `needs_review` (with `violations`); the CLI exits non-zero for it. `resume` re-runs the check of a `needs_review` run (the gate result is not restored). Thresholds are `OPENBLOG_QUALITY_*` environment variables; tests that are not about the gate pass lenient rules.

## ADR-020: Duplicates are blocked by default and allowed with `force`

- Context: a repeated topic only logged a warning and the run spent tokens and published again; different topics could produce the same slug or title.
- Decision: two checks. (1) `run()` stops right after `beginWorkflow` when a _published_ run exists for the normalized topic: outcome `duplicate`, zero provider calls, the run is stored with status `duplicate`, `is_duplicate = 1` and `duplicate_of_workflow_id`. (2) A `duplicate_check` node after `seo` looks the slug and title (case-insensitive) up in the stored articles of published or `needs_review` runs of other workflows, then asks the publisher (`findExisting`: WordPress searches the slug in any status, the markdown publisher looks for the file unless overwriting is enabled). A match ends the run as `duplicate` (`duplicate_slug`, `duplicate_title`, `duplicate_remote`); a lookup failure fails the step. `force` (`run({ force: true })`, CLI `--force`, or `OPENBLOG_ALLOW_DUPLICATES=true`) skips both stops, logs a warning and is stored in the run metadata (`{"force": true}`) and in the `duplicate_check` step output.
- Consequence: the CLI exits 3 for `duplicate` (ADR-023). Failed and parked runs never count as the original topic. `resume(id, { force })` re-runs the slug check. Semantic similarity is out of scope.

## ADR-021: Draft-by-default publication and an explicit `approve` step

- Context: only `OPENBLOG_WORDPRESS_STATUS` stood between model output and a live post, and a stored article could not be reviewed and published later.
- Decision: `OPENBLOG_PUBLICATION_POLICY` is `draft` (default), `publish_after_approval` or `publish_if_gate_passes`. After the quality gate passes: `draft` sends the article to the target with `status: "draft"` (WordPress draft; a markdown file with `status: draft`), `publish_after_approval` sends nothing, and only `publish_if_gate_passes` sends `status: "publish"`. The first two end the run as `awaiting_approval` (exit code 0, the log shows `approve <workflowId>`); a gate failure is `needs_review` under every policy and nothing is sent. `PublishArticle.status` wins over a publisher's own configured status, so `OPENBLOG_WORDPRESS_STATUS` only matters for direct publisher use. Articles carry a `review_state` (`needs_review` -> `approved` -> `published`), `gate_passed`, `approved_by`, `approved_at` and `approval_override_reason` (migration v3). `npm start -- approve <workflowId> [--override "reason"]` (`workflow.approve`) refuses unknown and already published articles, refuses an article that did not pass the gate (or whose gate result is unknown) unless an override reason is given, records the approver (OS user) and time, then publishes with `status: "publish"` through the idempotent publisher. A failed publish leaves the article `approved` so approving again retries it; a published one cannot be approved again. A markdown file is replaced by the live version only when it is the draft this publisher wrote.
- Consequence: `awaiting_approval` runs count as the original of a topic and their articles as slug/title collisions (ADR-020). `publish_if_gate_passes` is the only way a run publishes live on its own and is documented as risky. There is no command to list pending articles yet; the id is logged at the end of the run.

## ADR-022: The Docker image is a CLI runner

- Context: the image ran only the Fastify server (`/health`, `/version`), which cannot generate an article, and was not runnable: the runner stage copied `node_modules` but not `packages/*`, so the `@openblog/*` workspace links dangled. It also ran as root, used `npm install`, shipped dev dependencies and had no volumes.
- Decision: for the MVP the image's job is to run the CLI (`ENTRYPOINT node apps/cli/dist/index.js`); the server stays in the image (`--entrypoint node ... apps/server/dist/main.js`) but is not the default. Two-stage build on `node:20-bookworm-slim` (glibc, so `better-sqlite3` uses its prebuilt binary; Alpine would need a compiler): `npm ci`, `npm run build`, `npm prune --omit=dev`, then `apps/`, `packages/` and `node_modules` are copied so the workspace links resolve. Runs as the unprivileged `node` user. `OPENBLOG_MEMORY_DB_PATH` and `OPENBLOG_OUTPUT_DIR` default to `/app/data` and `/app/output/articles`, declared as volumes. No `HEALTHCHECK`, because a one-shot CLI has nothing to probe; add one when a server container is supported.
- Compose: `docker/docker-compose.yml` defines one `openblog` service with named volumes for data and output, an optional `../.env`, `restart: "no"` (a run ends by itself) and `host.docker.internal` so Ollama on the host is reachable.
- Consequence: CI builds the image and smoke-tests module resolution, the non-root user and volume persistence (`docker` job). Publishing images to a registry and Kubernetes are out of scope.

## ADR-023: CLI commands, flags and exit codes

- Context: the topic came from `process.argv` or the deprecated `npm_config_argv`, `start` rebuilt before every run, and exit codes were ad hoc.
- Decision: `node:util` `parseArgs` (no dependency) with commands `generate <topic>`, `resume <id>`, `approve <id>`, `list` and flags `--dry-run`, `--publisher`, `--force`, `--json`, `--override`, `--help`. Exit codes: 0 ok (published or awaiting approval), 1 failed (including thrown errors), 2 needs review, 3 duplicate, 64 usage (ADR-042 adds 10 nothing to do, 11 limit reached, 12 locked for `schedule run-once`). `--json` prints one summary object on stdout (`CliSummary` in `apps/cli/src/report.ts`; fields are only added); the default logger now writes to stderr so stdout carries only the result. `--dry-run` runs against a temporary copy of the SQLite database with a stand-in publisher that accepts everything: earlier runs are visible (duplicates, resume, approve) but nothing is stored, written or sent. `--publisher` overrides `OPENBLOG_DEFAULT_PUBLISHER` for the command. `apps/cli` has a `bin` entry (`openblog`); `start` and `generate` scripts no longer build.
- Consequence: `npm start -- <command>` needs a prior `npm run build`. Dry runs skip the remote duplicate lookup of the publisher. `list` shows the last 20 runs.

## ADR-024: Run-correlated structured logging with redaction

- Context: log lines were not tied to a run or step, failures lost context, Fastify had its own logger configuration, and nothing redacted secrets.
- Decision: the logger package keeps one pino configuration (`createPinoLogger`) with `redact` for known secret keys (top level and two levels down; `headers` is redacted wholesale) and `req`/`res` serializers that omit headers. Correlation uses `AsyncLocalStorage` (`withLogContext`), the same mechanism as LLM usage tracking: the workflow wraps `run`, `resume` and `approve` in a scope with `workflowId` (a throwaway UUID when there is no memory store) and each step in a scope with `step` and `attempt` (continuing the stored attempt count on resume). Everything logged inside, including provider retries that only know the shared logger, carries those fields; `withScope` gives any injected `ILogger` the same behavior, so no `child()` is needed on the interface. Steps log `Step finished` with `outcome` and `durationMs`; LLM calls log `LLM call completed` with provider, model, duration and tokens. Output goes to stderr; the shared logger is built on first use (so `.env` is loaded) and honors `OPENBLOG_LOG_LEVEL` and `OPENBLOG_LOG_PRETTY` (pino-pretty). Fastify receives the shared pino instance (`loggerInstance`).
- Consequence: redaction is key-based: a secret embedded in a free-text message is not caught (providers already sanitize error bodies). Metrics, tracing and log shipping stay out of scope.

## ADR-025: Documentation is checked against the code

- Context: the docs described intended structure, drifted from the code, and listed environment variables nobody could verify.
- Decision: `docs/configuration.md` documents every variable of the Zod env schema and `.env.example` lists each one; `scripts/check-docs.mjs` (`npm run check:docs`, run in CI after the build) reads the built schema and fails when a variable is missing from either, and fails on any broken relative link in `README.md` and `docs/`. The MVP is released as `0.2.0` (root `package.json` and tag `v0.2.0`; workspace packages stay private at `0.1.0`).
- Consequence: adding a variable requires documenting it in the same change. External links are not checked.

## ADR-026: Token usage per step and a per-run budget

- Context: the provider returned token counts but nothing stored them, so operators could not tell what an article cost or cap spending.
- Decision: the tracked LLM (`trackUsage`) adds prompt, completion and total tokens, call count and the provider-reported `cost` (OpenRouter, requested with `usage.include`) to the run's counter. Every step execution stores the difference it caused in new `workflow_steps` columns (migration v4), failed executions included. `list` sums them per run. `OPENBLOG_MAX_TOKENS_PER_RUN` and `OPENBLOG_MAX_COST_PER_RUN` set the budget: it is checked before every call and after every call, and throws `BudgetExceededError` (code `budget_exceeded`), so the step and the run fail with that code. On `resume` the stored usage of earlier executions is the starting point, so the budget covers the whole run.
- Consequence: cost comes only from what the provider reports (no price catalogs); with Ollama only the token limit applies. A call that crosses the limit has already been paid for, and its result is discarded. Steps stored before this change have no usage and count as zero.

## ADR-027: Optional LLM editorial review

- Context: the deterministic gate (ADR-018) only catches objective problems; judging SEO fit, readability or repetition needs a model, which costs money and has to be calibrated.
- Decision: an `editorial_review` node runs after `quality` only when `OPENBLOG_REVIEW_ENABLED=true` and the article passed the gate. The reviewer returns a 0 to 10 score for seo, readability, structure, completeness and repetition plus a rationale (through `generateStructured`); the overall score is the mean, computed in code. Below `OPENBLOG_REVIEW_MIN_SCORE` (default 7) the node sets `qualityPassed=false` and adds the error violation `editorial_review_below_threshold`, so the run ends as `needs_review` through the normal path and is not regenerated. The review is stored as a step output, so `list` and `--json` read it from there and `resume` re-runs a failed review. The node is not named `review` because LangGraph forbids a node with the name of a state channel.
- Consequence: when off, nothing changes and nothing is spent. A low score is not retried: regenerating on a subjective score could loop and spend without bound. The threshold is calibrated against stored fixtures with a fake provider only; tuning it against a real model is left to the operator.

## ADR-028: Authenticated HTTP API for runs

- Context: the server only had `/health` and `/version`, with CORS reflecting any origin and no authentication, which is unsafe for endpoints that spend money and publish.
- Decision: `apps/server` builds the application with `createApplication` (the CLI's wiring) and, given an application, registers `POST /runs`, `GET /runs`, `GET /runs/{id}`, `POST /runs/{id}/resume` and `POST /runs/{id}/approve` in an encapsulated plugin whose `onRequest` hook checks `OPENBLOG_API_KEY` (bearer token or `X-API-Key`, compared as SHA-256 digests with `timingSafeEqual`). Without a configured key the routes answer 503 rather than running open. Starting a run calls the new `workflow.begin()`, which stores the run as `started` and returns its id; `execute()` then runs in a `RunQueue` (`OPENBLOG_API_CONCURRENCY` running, `OPENBLOG_API_QUEUE_SIZE` waiting, else 429), and clients poll. `run()` is `begin()` plus `execute()`, so CLI and HTTP share one code path. `approve` is synchronous. CORS allows only `OPENBLOG_CORS_ORIGINS` (none by default). Routes carry JSON schemas, which Fastify uses to validate (unknown body fields are rejected) and `@fastify/swagger` turns into `/openapi.json`. Closing the server drains the queue before the store is disposed.
- Consequence: the queue is in memory, so queued runs are lost on a restart (they stay `started` in the store and can be resumed) and several server processes would not share a limit. One API key means every approval is recorded as `api` unless the client sends `approvedBy`. There is no per-client rate limiting and no dashboard.

## ADR-029: Ghost publisher on the Admin API

- Status: supersedes ADR-003
- Context: Ghost was removed in the MVP because the placeholder class made no request. A real target needs Admin API authentication, HTML content, tag handling and idempotency.
- Decision: `GhostPublisher` talks to `<site>/ghost/api/admin` with a hand-signed HS256 JWT (`node:crypto`, no dependency; `kid` is the key id, `aud` is `/admin/`, five minutes) created for every request, because a run can outlast one token. Content is sanitized HTML (`source=html`, the renderer WordPress already uses). Ghost has no categories, so the category is the primary tag. Before writing it looks the slug up (`/posts/slug/<slug>/`, any status) and updates with the post's `updated_at` (Ghost's collision check), never lowering a live post to draft, so repeating a publish updates instead of duplicating. The publisher is registered when `OPENBLOG_GHOST_ENDPOINT` is set and takes its key from `OPENBLOG_GHOST_ADMIN_API_KEY`, which is redacted like the other secrets. Errors use the same codes as WordPress.
- Consequence: only a fake server verifies it (offline contract tests that also check the JWT signature). Ghost's v5 payload shape is assumed (`Accept-Version: v5.0`); other major versions may differ. A concurrent edit in Ghost between lookup and update fails with `invalid_request` (409) instead of overwriting.

## ADR-030: The article brief as the workflow input

- Context: a run was described by its topic alone; audience, tone, keywords and length could not be given, and the writer prompt hard-coded a length that could disagree with the quality gate.
- Decision: `ArticleBrief` (`topic` plus optional `language`, `audience`, `tone`, `targetKeyword`, `secondaryKeywords`, `minWords`, `maxWords`, `notes`) is a strict Zod schema in `@openblog/types`, so agents, workflow, CLI and API share it without depending on each other. The CLI builds it from `--brief <file>` (YAML or JSON, parsed with `yaml`) overridden by flags, the API from the `POST /runs` body (JSON schema plus the same Zod check); a bad brief is exit 64 / HTTP 400 before a run is stored. The workflow input is the brief plus `force`; it stores the brief as given in the existing `workflows.metadata_json` (`{ "brief": ..., "force"?: true }`, so no migration) and `resume` reads it back (runs stored earlier fall back to their topic). The word range is resolved once per run: the brief's own bound, else `OPENBLOG_QUALITY_MIN_WORDS`/`MAX_WORDS`; the writer prompt and the quality gate use that same range. The state carries the resolved brief; results and `--json` report it. Planner, writer, editor and SEO prompts print the fields they can use in a `Brief:` block (nothing when the brief is topic-only) and their prompt versions are 2.
- Consequence: giving one bound that contradicts the configured other one (for example only `maxWords` below `OPENBLOG_QUALITY_MIN_WORDS`) is rejected, so both bounds should be given together. `language` was only passed on to the prompts at this point; ADR-031 makes it act. The workflow entry point still ignores unknown input fields (as before); the CLI and API reject them. Notes are free text from the operator and go into the prompts as written.

## ADR-031: Configurable content language

- Status: extends ADR-030
- Context: `language: "en"` was hard-coded in the published article (twice), no prompt named an output language, and `validateArticle` carried English-only phrase rules that would flag or miss text in other languages.
- Decision: `OPENBLOG_CONTENT_LANGUAGE` (a BCP-47-ish code validated by `languageCodeSchema` in `@openblog/types`, default `en`) is the default; the brief's `language` overrides it. The workflow resolves it once per run (`ResolvedArticleBrief.language`) and stores the resolved code in the run's brief metadata, so `resume` and `approve` keep the language the run was started with (older runs fall back to the configured one). The planner, writer, editor and SEO prompts state the language by its English name and code (`Intl.DisplayNames`, e.g. "Italian (it)"; prompt versions 3), and the SEO prompt demands a lowercase ASCII slug. The SEO schema still normalizes slugs (accents dropped, and now `ß æ œ ø đ ð þ ł ı` transliterated) and re-prompts when nothing ASCII is left, such as a slug in Japanese. `DEFAULT_PLACEHOLDER_PATTERNS` keeps only the language-neutral leftovers (`[...]`, `TODO`, lorem ipsum); the English and Italian disclaimer and placeholder phrases live in `LANGUAGE_PLACEHOLDER_PATTERNS` and `validateArticle` applies the ones of the article's primary language (`en` when unspecified). Outline coverage tokenizes with Unicode letters, so accented and non-Latin headings can match. The Markdown publisher already wrote `language` in the front matter; WordPress and Ghost have no language field in their payloads and are unchanged.
- Consequence: another language works but only gets the language-neutral phrase rules until its patterns are added to `LANGUAGE_PLACEHOLDER_PATTERNS`. A custom `forbiddenPatterns` now adds to, rather than replaces, the language's own phrases. Titles in scripts without a Latin transliteration depend on the model returning a romanized slug. The editorial review prompt is still English and does not receive the language.

## ADR-032: Per-step model routing

- Context: one model served every step, so cheap steps paid writer prices or the writer was limited to a cheap model.
- Decision: `GenerateRequest` gets an optional `model` that wins over the provider's configured one (OpenRouter and Ollama), which fits the provider contract with the least change. The workflow takes `models` (`planner`, `writer`, `editor`, `seo`, `classification`, `review`), filled by `createApplication` from `OPENBLOG_MODEL_*`; each agent gets the shared usage-tracked LLM wrapped to add its model, so the usage counter and the budget stay one per run and the workflow still depends on the port only. Regenerations go through the writer and use its model. The fallback chain does not forward `model` to the fallback provider: an OpenRouter id would not exist in Ollama, which uses `OLLAMA_MODEL`. Each step execution stores the distinct models the providers reported (`model`, comma-separated if a fallback changed it mid-step; migration v5 adds a nullable `workflow_steps.model`). `list` returns `models` (latest model per step) and the run details return `model` per step.
- Consequence: runs stored before this have no model (null). A misspelled model id fails the step as the provider answers. When Ollama is the primary provider (no OpenRouter key) the per-step values are sent to it as model names. No price catalog or automatic selection.

## ADR-033: Reject and revise stored articles

- Context: `approve` (ADR-021) was the only human decision; a reviewer could not close an article for good or ask for changes, and the workflow's `regenerate` loop took only machine feedback.
- Decision: a new terminal run status `rejected` (and article review state `rejected`) and two commands. `reject` needs a reason and applies to `needs_review` and `awaiting_approval` runs; it sets the status, never touches the target, and `approve`, `revise`, `reject` and `resume` refuse it (`already_rejected`). Duplicate detection only counts `published`, `awaiting_approval` and `needs_review` runs, so a rejected article frees its topic, slug and title. `revise` needs feedback and the same two statuses. It does not start a new run: it executes the same run again from the writer, restoring only the outline (the stored brief is reused) and putting the reviewer's feedback and the version they read (`previousArticle`) in the state; the writer prompt shows both, next to any machine feedback from a later regeneration. Every node after the planner runs again, so the revised article goes through the same gate, review, classification and publication policy; its prior token usage seeds the budget like `resume`. A draft that this run already sent under the same slug is not a duplicate of itself (`ownSlug`), and the publisher gets `revisesDraft` so the Markdown publisher may replace its own draft file; WordPress and Ghost already update by slug. Decisions are rows of the new `workflow_decisions` table (migration v6: action, actor, note, time) returned as `decisions` by `GET /runs/{id}`. `ReviewError` carries the codes `memory_unavailable`, `not_found`, `already_published`, `already_rejected`, `invalid_state`, `invalid_input`; the API maps them to 503, 404, 409, 409, 409, 400. `revise` validates before it returns a `PendingRun`, so the API can refuse before queueing and the CLI runs it directly. `POST /runs/{id}/revise` goes through the run queue; `reject` is synchronous.
- Consequence: a rejected remote draft stays on the target until someone deletes it. A `failed` run is resumed, not revised. The actor is the OS user for the CLI and `api` (or `rejectedBy`/`revisedBy`) for HTTP, not an authenticated identity. A revision keeps the old steps, so the step history shows several writer attempts. The status of a run being revised stays `needs_review`/`awaiting_approval` until the queue starts it.

## ADR-034: Recovering runs abandoned by a dead process

- Context: a killed process or a restarted server left runs in `running`/`started` forever (ADR-028), so `list` showed them as active and a scheduler could not tell a live run from a dead one.
- Decision: a new run status `interrupted` (the column is plain text, no migration). `MemoryService.recoverStaleRuns(staleAfterMinutes, now)` moves `started`/`running` runs to it when neither the run row nor any of its steps was written since the cutoff, so a long step in a live run is not mistaken for a dead one as long as steps are shorter than the threshold; the clock is a parameter, so tests inject it. Steps are untouched. It runs at server startup (logging the count) and on demand with `list --recover-stale`, never implicitly on other CLI starts, because a second CLI process cannot know that another live process owns a run. `resume` already accepted every status but `published` and `rejected`, so it needs no change; `markRunning` sets the run back to `running`.
- Consequence: a single step longer than `OPENBLOG_RUN_STALE_AFTER_MINUTES` can be marked interrupted while it is still running, and resuming it would then run in parallel; keep the threshold above the longest expected step. There is no lock across processes (out of scope), which the M8 scheduler lock builds on.

## ADR-035: Keyword coverage in the quality gate

- Context: the brief carries a `targetKeyword` (ADR-030) but nothing checked that the article and its metadata target it, so SEO targeting depended on the model following the prompt.
- Decision: `validateArticle` takes an optional `keyword` (the workflow passes the brief's `targetKeyword`). Only when it is set, the gate adds errors `keyword_missing_in_title`, `keyword_missing_in_meta`, `keyword_missing_in_h2` (no H2 contains it) and `keyword_missing_in_intro` (the prose before the first H2, or the whole article when there is none), plus `keyword_density_low` / `keyword_density_high` when the keyword's words as a share of the article's words fall outside `OPENBLOG_QUALITY_KEYWORD_MIN_DENSITY` / `MAX_DENSITY` (defaults 0.005 / 0.03). Matching compares lowercase, diacritic-free word sequences, so `Caffe` matches `CAFFÈ` but `cache` does not match `caching` (no stemming); a multi-word keyword counts as one occurrence per phrase. The violations go through the existing regeneration feedback (ADR-019), which re-runs the writer, editor and SEO steps, so a missing title or meta is fixed by the next SEO pass.
- Consequence: a keyword the model cannot place naturally ends the run as `needs_review` after the allowed attempts. Inflected forms and synonyms count as misses, which is stricter in languages with rich morphology; secondary keywords, search volume and SERP analysis are out of scope.

## ADR-036: Prompt overrides from a directory

- Context: an operator could not set a house style without forking, because the prompts are built in code (`packages/agents/src/prompts`).
- Decision: `OPENBLOG_PROMPTS_DIR` holds optional `<agent>.md` files. Each prompt is split into the part an operator may replace (role and style instructions) and the part code depends on: the output language and brief lines, the JSON structure and rules that `generateStructured` parses, the data (outline, article text) and, for the writer, the requirements `validateArticle` enforces (no H1, H2 sections, word range). An override replaces the first part and the rest is appended exactly as before, so the default prompt is byte-identical (snapshot tests) and an override changes style, not the contract. The syntax is `{{name}}` with a fixed allowed set per agent (`PROMPT_PLACEHOLDERS`), no template engine; unset values render as nothing. `loadPromptOverrides` (in `@openblog/app`, so the agents stay free of file access) runs first in `createApplication`, so an unknown placeholder, a stray `{{`, an empty or unreadable file, a missing directory, or a planner/writer file without `{{topic}}` stops every CLI command and the server with a message naming the file, before a database is opened or a run starts. The overrides travel to the workflow as `prompts` and to each agent as `promptTemplate`. The record of which prompt a run used is a per-step hash: `trackUsage` hashes (SHA-256) every prompt it sends, and the step wrapper stores the first one of the execution in `workflow_steps.prompt_hash` (migration v7); `GET /runs/{id}` returns it as `promptHash`.
- Consequence: the hash covers the whole prompt including the article text, so it identifies what one step sent, not the style text alone; compare the override file itself (its content is logged only by agent name at startup) to see a house style change. Retries inside a step (structured-output re-prompts) are not hashed separately. The `{{topic}}` requirement is an addition to the issue's scope, to keep a planner or writer from running without a subject. The prompt versions (`*_PROMPT_VERSION`) describe the built-in text and do not change; the `prompts` table still stores the planner and writer prompts as sent. No prompt editing UI and no A/B testing.

## ADR-037: Upgrade `@langchain/langgraph` to 1.5

- Context: `packages/graph` pinned `^0.2.39` (0.2.74 installed). The latest stable is 1.5.2 (npm `latest`, 2026-10-21), a new major.
- Decision: upgrade. The 1.x line needs `@langchain/core` ^1.1.48 (installed as its peer, 1.3.0) and `zod` ^3.25.32 (the lockfile already had 3.25.76); `engines` stays Node >=18, inside the CI matrix (20, 22). The only code change is typing: graph `Update` types now also admit overwrite markers (`T | OverwriteValue<T>`), so `ArticleWorkflowUpdate` is `Partial<ArticleWorkflowState>` instead of `typeof graphState.Update` (nodes still return plain values, and the graph accepts them). The `Annotation.Root` state, `StateGraph` wiring, the node naming rules of ADR-027 and the conditional edges work unchanged. No test was changed or weakened: build, typecheck, lint, `check:deps`, `check:docs` and the full suite (399 tests, including the e2e workflow and resume tests) pass.
- Consequence: three extra transitive packages from the 1.x line (`@langchain/protocol`, newer `langgraph-sdk` and `langgraph-checkpoint`) enter the lockfile although checkpointers stay unused (ADR-015). Future upgrades within 1.x are expected to be routine; the dependency range is `^1.5.2`.

## ADR-038: One safe fetcher for external content

- Context: M8 reads URLs supplied by operators and feeds. The server also exposes an API (ADR-028), so a fetch that follows any URL could be used to reach internal services or cloud metadata (SSRF).
- Decision: a new package `@openblog/research` holds the `ContentFetcher` port and its only implementation, `SafeContentFetcher`; the graph re-exports the port as `ContentFetcherPort` and never imports the implementation (ADR-010), and `createContentFetcherFromConfig` in `@openblog/app` builds it from `OPENBLOG_FETCH_*`. For every hop (first request and each redirect) it accepts only `http`/`https` without credentials, checks the host allowlist, resolves the name and refuses it when any answer is loopback, private, link-local, CGNAT, multicast, reserved or a metadata address (`isPrivateAddress` also judges the IPv4 inside IPv4-mapped, NAT64 and 6to4 IPv6 addresses; literal IPs in URLs are checked the same way and WHATWG parsing normalizes decimal/hex forms). The default transport (`node:http`/`https`) then connects to the address that passed the check through a custom `lookup`, so a second DNS answer cannot change it (no DNS rebinding), while TLS still validates the certificate for the requested name. One deadline covers the whole fetch; the body is counted while read and the connection dropped at `OPENBLOG_FETCH_MAX_BYTES`; only identity encoding and HTML/XHTML/XML/RSS/Atom/plain-text types are accepted. Errors are `FetchError` with the codes `fetch_blocked`, `fetch_timeout`, `fetch_too_large`, `fetch_http_error`, `fetch_unsupported_type` and, added to the issue's list, `fetch_network` for DNS and connection failures; URLs in errors and logs lose credentials and query (ADR-024).
- Consequence: `robots.txt`, caching, compressed responses, proxies and headless rendering are not handled. The allowlist is exact hostnames, not wildcards. A fetch through a system HTTP proxy is not supported (the connection is made directly). Tests inject a resolver and a transport, plus a local server with `OPENBLOG_FETCH_ALLOW_PRIVATE`-style access, so `npm test` needs no network. The port is not used by the workflow yet; the feed collector (#80) is its first consumer.

## ADR-039: Topic sources: deterministic collection from feeds and sitemaps

- Status: extended by ADR-040
- Context: the topic of every run was typed by a human. M8 starts by collecting candidates from places the operator already trusts, without a model.
- Decision: `@openblog/research` gets a `TopicSource` contract with two implementations, `FeedTopicSource` (RSS 2.0, RSS 1.0/RDF, Atom) and `SitemapTopicSource` (`urlset` and `sitemapindex`, at most 3 nested documents, 20 child sitemaps and 1000 entries per source, child sitemaps only on the index's own site). Both read only through the `ContentFetcher` port (ADR-038). XML is parsed with `fast-xml-parser` (maintained, no native code, one small dependency tree), after `XMLValidator`, so malformed documents are reported instead of half-parsed. Sources come from `OPENBLOG_RESEARCH_SOURCES_FILE` (YAML/JSON, strict Zod schema: `name` unique, `type` `feed|sitemap`, http(s) `url`, `weight` 0-10 default 1, `include`/`exclude` keywords matched case-insensitively against title, summary and URL). A candidate is `title`, canonical `url`, `source`, `weight`, optional `publishedAt` (ISO) and `summary` (plain text, 500 characters). Titles and summaries lose markup and entities; sitemap titles are made from the last path segment. URLs are canonicalized (lowercase host, no fragment, default port or tracking parameters such as `utm_*`, `fbclid`, `gclid`; sorted query; no trailing slash). `collectTopicCandidates` runs the sources in parallel, isolates each (a `SourceReport` with `ok|failed`, count, error code and warnings), and merges entries that share a URL (scheme and `www.` ignored) or a normalized title, using `normalizeTopic`, which moved from `MemoryService` to `@openblog/types` so duplicate detection and research share one definition. The heavier source wins a duplicate (the first on a tie) and lends the other's date or summary when it lacks them; the result is sorted newest first. `collectTopics` in `@openblog/app` wires the file and the fetcher; `openblog research collect` uses it without building the application, so it needs neither a database nor a model, and exits 1 only when every source failed.
- Consequence: nothing is stored; the backlog (#81) adds persistence, scoring and the accept/drop decisions. HTML listing pages, compressed sitemaps (`.xml.gz`), feeds that need authentication, and web search or trend sources are out of scope; the latter fit behind `TopicSource` later. A sitemap yields thin candidates (title from the slug, date from `lastmod`). Title dedup is exact after normalization, so a reworded title from another source stays a separate candidate. Keyword filters are substring matches, not word matches (`ai` also matches `maintain`).

## ADR-040: The topic backlog

- Context: collected candidates (ADR-039) need to live somewhere and wait for a human before they cost money; the `topics` table only counts topics that already ran.
- Decision: migration v8 adds `topic_candidates` (title and normalized title, URL and canonical URL key, source, summary, published and collected dates, integer score, JSON breakdown, motivation, status `new|accepted|dropped|used`, optional JSON brief, who and why and when for the decision, the run's id once used). The normalized title and the URL key are both `UNIQUE`, which is what makes collection idempotent: `TopicBacklogStore.upsertCollected` looks a candidate up by URL key, then by title; a missing one is inserted, one still `new` gets its score, breakdown and motivation refreshed (and may become auto-accepted), a decided one is untouched, so a dropped candidate never comes back as `new`. Scoring is the pure `scoreCandidate` (clock injected): recency 0-40 (linear over 30 days, 10 undated), source weight 0-30 (weight 2 or more is full, the default 1 is half), +10 per matched include keyword (max 20) and -20 per excluded one (max 40), and -60 times the Jaccard overlap of significant words when it is at least 0.4 against the topics and titles of published, awaiting-approval and needs-review runs; the sum is clamped to 0-100. A title identical to such an article is skipped (reported in `skipped`, not stored) instead of scored down. `createResearchService` in `@openblog/app` joins collection, scoring and the store and is exposed as `Application.research` (absent without the SQLite store); the CLI (`research collect`, `topics list|accept|drop|generate`) and the server (`GET /topics`, `POST /topics/collect|{id}/accept|{id}/drop`, behind the API key) only call it. Decisions need a person (`accepted` by the CLI user or the API caller) unless `OPENBLOG_RESEARCH_AUTO_ACCEPT_MIN_SCORE` is set, in which case the decision is recorded as `auto`. `accept` takes brief fields without the topic (`candidateBriefSchema`) that `topics generate` merges under its own flags; the topic is always the candidate's title. `generate` runs the normal workflow (`new` or `accepted` candidates) and then marks the candidate `used` with the run id, so the duplicate policy, quality gate and publication policy are unchanged. `ResearchError` lives in `@openblog/research` and `BacklogError` in `@openblog/storage`, so the server can recognize them whichever package built them. Ids may be shortened to a unique prefix of 4 or more characters.
- Consequence: a stored score is as of the last collection (the recency of an old candidate is not recomputed until it is collected again, and a candidate that stops appearing in its feed keeps its last score). A candidate that becomes covered after it was stored stays `new` until a person drops it. A run started from a candidate by other means does not mark it `used`. `topics generate` marks the candidate after the run returns, so a crash in between leaves it unmarked. The source URL is stored but not yet given to the writer (grounded generation is a separate issue). Semantic similarity is out of scope (M9).

## ADR-041: Grounded generation from source pages

- Context: articles were written from the model's memory; a topic found in a feed got stale or invented facts and no references.
- Decision: the brief gets `sources` (1 to 5 http(s) URLs, `MAX_BRIEF_SOURCES`). The graph depends on a `SourceReaderPort` (`read(url, { maxChars })` returning `url`, `finalUrl`, `title`, `text`, `truncated`), implemented by `createSourceReader(fetcher)` in `@openblog/research`: it reads only through the safe fetcher (ADR-038), so address rules, limits and redaction apply, extracts the text with a small built-in extractor (no dependency: it drops scripts, styles, navigation, header, footer, aside, forms and comments, prefers the longest `<article>`, else `<main>`, else `<body>`, and keeps paragraphs, headings as `## ` and list items; a library such as Readability needs a DOM implementation, which is far heavier than this need) and refuses pages with fewer than 200 readable characters (`source_empty`). A new graph node `read_sources` (not `sources`, which is already the state field, ADR-027) runs before the planner only when the brief has sources, through a conditional edge from `START`, so a run without sources has the same steps, prompts and calls as before. Pages are read in order; each gets an equal share of `OPENBLOG_SOURCES_MAX_CHARS_TOTAL`, never more than `OPENBLOG_SOURCES_MAX_CHARS_PER_SOURCE`. The extractions are the step's stored output, so `resume` and `revise` (which keeps the outline and now also the sources) reuse them. A page that fails stops the run at the step with the fetcher's code, `source_empty`, `sources_unavailable` or, with `OPENBLOG_SOURCES_ALLOW_PARTIAL=true` and every page failing, `sources_failed`; with the option on, failed pages are skipped, logged and stored as `skippedSources`. The planner and writer prompts add the texts in `<source url title>` blocks after a warning that they are untrusted and their instructions must not be followed; a closing tag inside a page is escaped so a page cannot end its block. The writer must end with a references section titled in the article's language (`referencesHeading`: English, Italian, Spanish, French, German, Portuguese, else `References`) linking only to the sources; the editor is told to keep it. `validateArticle` takes `sources` (the requested URLs and the final URLs after redirects) and adds `references_missing` (no link to any of them) and `reference_not_provided` (any other http(s) address in the text); URLs compare ignoring scheme, `www.`, fragment, trailing slash and `utm_*`. `topics generate` adds the candidate's page as the source when the brief names none.
- Consequence: the prompts grow by up to `OPENBLOG_SOURCES_MAX_CHARS_TOTAL` characters. Prompt versions are unchanged since the built-in text is the same without sources. The gate forbids every other link, including legitimate ones to documentation the model knows; that is the point of the rule but it can park an article that links outward. Pages that need JavaScript, PDFs and paywalls give `source_empty` or `fetch_unsupported_type`. Nothing checks that the claims match the sources (out of scope), and a hostile page can still try to bend the writer: the delimiters and the warning lower the risk, they do not remove it, which is why the publication policy keeps a human before anything is live. A source cannot be given in a prompt override placeholder.

## ADR-042: `schedule run-once` for external cron

- Context: every run was started by hand. The pipeline now has a backlog of accepted topics (ADR-040) and recovery of dead runs (ADR-034), so one idempotent command can do the next unit of work from cron.
- Decision: `SchedulerService.runOnce` in `@openblog/app`, exposed as `Application.scheduler` and `openblog schedule run-once [--collect]`. The lock is a row of `scheduler_locks` (migration v9: name, owner, acquired and expiry times) taken in an immediate SQLite transaction, so two callers, in one process or in two, never both get it (the owner is `host:pid:random`, new for every call, which is what keeps two calls of one process apart). A lock past its expiry is taken over (`OPENBLOG_SCHEDULE_LOCK_TTL_MINUTES`, default 120); it is released in a `finally`. Order: lock, recover stale runs, collect (if asked), time window and limits, pick, run. Limits look at the last 24 hours rather than a calendar day, so there is no time zone to get wrong and they hold across restarts because they are computed from the stored runs (`created_at`, every run counts, manual ones too) and steps (`cost_usd` of steps finished in the window); a limit is a clean no-op reported with its `reason` (`max_runs_per_day`, `max_cost_per_day`, `outside_window`). The window is `HH:MM-HH:MM` in the process's local time and may cross midnight. The candidate is the highest-scored `accepted` one (`topics`' own ordering); the run is registered with `workflow.begin`, the candidate marked `used` with its id, and only then executed, so a crash leaves a resumable run and not a candidate that would be run again. The brief is the stored one with the candidate's title as topic and its page as the source (ADR-041). Exit codes: the run's own (0, 1, 2, 3) when one ran, `10` nothing to do, `11` limit reached, `12` locked; `--json` carries the status. `--dry-run` uses the throwaway database copy of ADR-023. The Compose `scheduler` service (profile `scheduler`) loops the command with `--collect` every `OPENBLOG_SCHEDULE_INTERVAL_SECONDS`; CI validates the file with that profile enabled.
- Consequence: a failed run is not retried by the scheduler (its candidate is `used`); an operator resumes it or re-accepts a new candidate. The cost limit is checked before a run starts, so one run can overshoot it by its own cost (the per-run budget of ADR-026 bounds that). The lock does not span hosts or databases, and nothing runs inside the server. A run that outlives the lock TTL lets a second `run-once` start, so keep the TTL above the longest run. A scheduled run produces what the publication policy says, a draft by default.

## ADR-043: Webhook notifications

- Context: with scheduled runs (ADR-042), articles parked as `awaiting_approval` or `needs_review` and failed runs were invisible until someone ran `list`.
- Decision: a `NotifierPort` (`notify(notification)`, from the new `@openblog/notify` package, like `LlmPort` from providers) is called by the workflow right after the outcome of a run is stored: from `execute` for `published`, `awaiting_approval`, `needs_review` and a publisher `failed`, from its error path for a failed step (`budget_exceeded` when the error code says so, else `failed`), and from the duplicate stop; `resume` and `revise` go through `execute`, so they notify again. `approve` and `reject` are human decisions and do not. The scheduler notifies `schedule_limit_reached` for the daily run and cost limits but not for the time window, which is the normal state of a night schedule. The webhook notifier filters by `OPENBLOG_NOTIFY_EVENTS` (names validated at startup, default the four that wait for a person), so each configured event sends exactly one message per occurrence. Bodies: a generic JSON object with a stable shape, or a Slack (`text`) or Discord (`content`, at most 1900 characters) message; errors are cut to 300 characters. Delivery is `fetch` with a 10-second timeout per attempt and 3 attempts (0.5 s then 1 s) on network errors, timeouts, `429` and `5xx`; other `4xx` are not retried. Whatever happens, `notify` returns, and the workflow also catches anything thrown, so a notification never fails or alters a run. The URL is a secret: it is in `SECRET_ENV_KEYS`, `webhookUrl` and `OPENBLOG_NOTIFY_WEBHOOK_URL` are redacted keys of the logger, logs carry only the host, and an error message that quotes the URL has it replaced. `OPENBLOG_NOTIFY_BASE_URL` turns the run id into a `GET /runs/{id}` link.
- Consequence: delivery is in the run's path, so a dead webhook adds up to about 33 seconds (3 timeouts plus the pauses) to the end of a run, which matters little for background runs. There is no persistent outbox: a notification lost with the process is not re-sent. The webhook is called directly rather than through the content fetcher (ADR-038), because the operator configures it and an internal chat gateway is a legitimate target; it must therefore not be pointed at an address an attacker can choose. No email, push or interactive approval from chat.
